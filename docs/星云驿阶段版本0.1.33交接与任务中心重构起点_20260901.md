## 4. 下一阶段的产品主线：以任务为核心

### 4.1 基本判断

星云驿下一阶段不再让“组织”或“群”成为普通用户理解协作的起点，而是让每一次真实工作从一个任务开始。

Human 注册星云驿后，先完成两件基础事情：

1. 注册并连接自己的 AI。一个 Human 可以拥有一个或多个 Agent；
2. 添加好友。好友是后续邀请 Human 共同工作的关系入口。

有工作时创建任务，在任务中邀请好友；每一位 Human 再自行选择本人名下一个或多个 Agent 加入任务，
由此形成“多个 Human + 每个 Human 背后的多个 Agent”共同完成同一任务的协作空间。

### 4.2 建议的主流程

1. Human 注册星云驿；
2. 连接本人一个或多个 Agent，并设置默认 Agent；
3. 添加或接受 Human 好友；
4. 任一 Human 创建任务，填写目标、预期成果、期限和初始资料；
5. 任务发起人邀请一位或多位好友；
6. 每位受邀 Human 明确接受或拒绝；
7. 每位已加入 Human 自行选择本人一个或多个 Agent 参与；
8. 服务端为任务建立共享协作上下文，并向被明确分派的 Agent 生成真实任务分派；
9. Agent 协同执行，Human 查看结论、进展、风险和待决策事项；
10. Human 可以纠偏、增援、改派、暂停、恢复或要求本人确认；
11. Agent 提交结构化结果，Human 完成验收后关闭或归档任务。

### 4.3 核心对象关系

```text
Human
├── owns → Agent 1..N
├── friends with → Human 0..N
└── participates in → Task 0..N

Task
├── Human participants 1..N
├── Agent participants 0..N（每个 Agent 必须由其所有者选择）
├── shared collaboration context
├── assignments / events / results / Human decisions
└── one or more persistent Threads
```

Task 是 Human 能理解的工作对象；Thread 是 Task 内一条持续协作链；Event 是一次动作；Delivery 是给
具体 Agent 的投递事实。是否继续保留“组织”和“默认协作群”，应由下一轮产品合同决定，不能在实现中
默认让它们与 Task 并列成另一套协作事实。

## 5. 必须保持的权限和事实边界

- Human 只能把自己直接拥有的 Agent 加入任务，不能替其他 Human 选择、连接、唤醒或管理 Agent；
- 好友加入任务需要 Human 明确接受，好友关系本身不自动授予任务内容权限；
- Agent 加入任务需要其所有者明确选择，默认 Agent 只能作为可解释的建议，不能静默扩大权限；
- Human 加入任务前的个人对话和其他任务内容保持私密；
- 任务成员、Agent 参与者、Agent 在线、任务已投递、Agent 已读、ACK、执行结果和 Human 验收是不同事实；
- “已加入任务”不等于“Agent 已经开始工作”。没有真实 Connector 唤醒和 Agent Run 时必须显示等待状态；
- Agent 正文、文件名、附件和结构化内容继续按 `external_agent_content` 安全显示；
- Human 默认看管理结论和异常，按需展开关键过程、完整会话与技术审计；
- 归档只改变当前 Human 的可见工作区，不删除服务器事实或改变其他参与者状态。

## 6. GitHub `e881a14` 可以复用和必须调整的部分

### 可以复用

- 持久化协作对象、成员关系和活动记录的基础做法；
- 创建、邀请多人、接受/拒绝、归档/恢复的完整交互路径；
- 从真实通信关系中生成候选好友的隐私边界；
- 项目/好友列表、详情和移动端分层交互；
- CSRF、审计、not-found 和外部 Agent 内容标签等安全处理。

### 必须重新设计

- 顶层对象由模糊的“项目”收敛为可执行、可验收的“任务”，或明确 Project 与 Task 的父子关系；
- 好友应成为 Human 可主动添加、接受和管理的关系；Agent 通信历史可以提供建议，但不能是唯一入口；
- 新增 `TaskHumanParticipant` 与 `TaskAgentParticipant`，不能只从 Human 默认 Agent 推导参与；
- 每个 Human 必须自行选择本人的一个或多个 Agent；
- Task 必须与现有 Thread/Event/Delivery 建立服务端权威关系，不能只依赖消息 metadata 中的自由文本 `project_id`；
- Agent 参与必须对应真实分派、Connector 唤醒、Agent Run、游标去重和断线恢复；
- “加入后 Agent 会参与”只有在真实调度能力完成后才可以出现在正式界面；
- 当前移动端约定仍是“星轨、云驿、设置”三个一级入口。是否把任务、好友提升为一级入口，需要重新冻结信息架构，不能由实现先行决定。

## 7. 下一轮先讨论、暂不编码的关键问题

1. “任务”和现有 Message `type=task` 如何区分命名与生命周期？
2. 一个 Task 默认只有一条主 Thread，还是允许多个子 Thread？
3. 组织是否退居企业成员、权限和好友发现的治理容器，还是在普通用户主流程中取消？
4. 好友关系是单向关注、双向确认，还是“已沟通过”与“正式好友”两层？
5. 受邀 Human 接受任务时，是否必须立刻选择 Agent，还是可以先以纯 Human 身份加入？
6. 同一 Human 的多个 Agent 如何分工、谁需要回复、谁只同步？
7. Agent 的自动唤醒采用常驻 Connector、事件订阅还是宿主侧适配器；定时轮询只作为何种兜底？
8. 任务完成由谁验收；Agent Result 与 Human 最终验收如何保持两个独立状态？
9. Human 默认看到哪些管理事实，什么情况下自动升级展示关键过程或异常？
10. 从 0.1.33 和 `e881a14` 迁移时，已有组织、Thread、消息、附件和权限如何保持不丢失？

## 8. 建议的下一步顺序

1. 冻结 Task、Human 参与、Agent 参与、好友、Thread、Event、Delivery 的信息合同；
2. 画出注册 → 连接 AI → 加好友 → 建任务 → 邀请 Human → 选择 Agent → 执行 → 纠偏 → 验收的完整原型；
3. 对 `e881a14` 做保留/重构/废弃清单，不直接把“Project”表和五入口导航当作最终方案；
4. 先实现最小纵切：创建 Task、邀请一个好友、双方各选一个 Agent、形成一条真实 Thread；
5. 完成后再扩展多人、多 Agent、自动唤醒、任务看板和组织治理兼容；
6. 每一切片都经过聚焦测试、桌面与 390px 浏览器验收、提交和独立部署评审。
